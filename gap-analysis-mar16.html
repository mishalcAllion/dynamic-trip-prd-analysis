Critical Gaps

Blocks development or will cause incorrect implementation if not resolved immediately
G1
Section 7.11 Error & Empty States -- Truncated
Critical PRD
Where
PRD Section 7.11 -- the heading Error & Empty States exists, but the content beneath it is missing. The section appears to have been truncated or never completed.
Impact
Devs have zero spec for error handling, loading states, empty trips, or network failures. Without this, every developer will invent their own patterns, leading to inconsistent UX across the trip page. This includes: what to show when a trip has no components, what happens on API timeout, retry logic UX, skeleton vs spinner loading, and 404/permission error screens.
Owner
Sunthar / Nirav (PM) to spec the full section before Sprint 9 development begins
G2
Comments Model Inconsistency -- PRD Contradicts Itself
Critical PRD Mar 13 Meeting
Where
PRD Section 7.2 says "append to Comments JSON array", implying a JSON-based threaded comment model. However, Section 6.2 defines the data model with two plain text fields: Client Request and Ops Response. The Mar 13 engineering meeting explicitly confirmed the two-text-fields model.
Impact
Backend devs will build the wrong data model if they follow Section 7.2. Section 6.2 and the Mar 13 decision both say two text fields -- but Section 7.2 describes JSON array append logic. A developer reading sequentially will hit Section 7.2 first and may implement the wrong pattern before reaching Section 6.2.
Owner
Sunthar + Tharaka to correct PRD Section 7.2 to match the confirmed two-text-field model
G3
Auth Flow Undefined
Critical PRD
Where
PRD Section 7.2 references "existing auth flow" with no further details. No endpoint, no token format, no session management spec.
Impact
Kalpa needs to know: JWT? Session tokens? How does a mobile user map to their Notion member record? The Dynamic Trip Page pulls member-specific data (their trip, their approvals, their comments). Without a documented auth contract, the API layer cannot correctly scope data to the authenticated user.
Owner
Kalpa + Yasiru to document the existing auth flow and confirm it supports member-level data scoping
G4
Task Dedup/Batch Logic -- No Implementation Pattern
Critical PRD
Where
PRD Section 7.9 describes business rules -- 5-minute dedup window and 3+ actions in 2 minutes = batch task -- but provides no implementation approach.
Impact
Shashila needs to know: in-memory dedup? Redis queue? Debounce timer? What happens on server restart -- are pending tasks lost? The rules are clearly defined but the technical mechanism is not. Without an architectural pattern, the implementation will be fragile or over-engineered.
Owner
Tharaka (architect) to define the implementation pattern and persistence strategy

High-Priority Gaps

Significant risk if not resolved before Sprint 9 kickoff or early in the sprint
G5
Award Flight Automation (P2.8) -- No Spec
High PRD Mar 13 Meeting
Where
Referenced in both the PRD and Mar 13 meeting as TBD. No spec exists for the automated pipeline that populates trip component cards with award flight data.
Impact
Thiranjaya + Andy cannot start. Ops manual entry is the MVP fallback, but there is also no fallback UI spec for manual component entry. Without either an automation spec or a manual entry spec, flight components will have no data population path.
Owner
Thiranjaya + Andy to spec the automation pipeline in Sprint 9. Sunthar to confirm if manual entry fallback needs a UI spec.
G6
Notification Deep Linking -- No Endpoint Spec
High PRD
Where
PRD Section 4.8 lists 4 notification triggers with throttle rules, but defines no deep link URL scheme or routing spec for where those notifications navigate to within the app.
Impact
Push notifications will link to the app but cannot navigate to the right trip or component without a URI scheme. Users tapping a "Your hotel is ready for approval" notification need to land on the specific component card, not the app home screen.
Owner
Kalpa (routing) + Waruna (screen mapping) to define the deep link URI scheme
G7
Lazy Loading Strategy -- Implementation TBD
High PRD Mar 13 Meeting
Where
PRD Section 7.10 describes the intent -- prefetch on scroll, skeleton loading -- but the Mar 13 meeting noted that Kalpa has not yet confirmed the implementation approach.
Impact
Trips with 15-30 components could be slow to load without a confirmed strategy. Luxury travelers expect premium app performance. A 3-5 second load time on a complex trip page would be noticeable and unacceptable for the target demographic.
Owner
Kalpa to confirm the lazy loading approach in Sprint 9 planning
G8
Offline/Connectivity Handling -- Not Mentioned
High Absent from all sources
Where
Absent from the PRD entirely. Not discussed in the Mar 13 meeting. Not represented in the analysis tool.
Impact
Luxury travelers are often on planes, weak hotel wifi, or roaming internationally. No spec exists for: cached trip data, offline viewing of previously loaded trips, retry logic on failed actions, or connectivity banners. A user approving a hotel component on airplane wifi with no retry logic will see a silent failure.
Owner
Sunthar to decide scope -- at minimum, a connectivity banner and retry logic for V1
G9
Component Perks/Benefits Data Source
High Mar 13 Meeting
Where
Mar 13 meeting mentions "fora" perks for hotel components, but there is no Notion field defined for perks and no parsing contract for how perk data reaches the mobile app.
Impact
The hotel detail view (S2) shows a perks section, but there is no defined data source to populate it. Without a Notion field or API contract, the perks section will either be empty or require hardcoded placeholder data -- neither is acceptable for production.
Owner
Nirav to clarify the Notion field and data source for component perks/benefits

Medium / Low Gaps

Should be addressed but will not block the April 15 MVP ship date
G10
Experience Component Type-Specific Schema
Medium Mar 13 Meeting
Where
Mar 13 meeting: "hours or ticket price or whatever" for experience components -- an incomplete, informal description of the schema for non-flight, non-hotel component types.
Impact
Experience cards may render inconsistently. Each component type (hotel, flight, experience, restaurant, transfer) likely needs different display fields. Without a per-type schema, Waruna will design cards with placeholder fields that may not match real data.
Owner
Nirav to define per-type schema (minimum fields per component type)
G11
No Accessibility Requirements
Medium Absent from all sources
Where
Absent from the PRD. No accessibility standards are referenced anywhere in the document.
Impact
The mobile app should meet WCAG 2.1 AA minimum -- contrast ratios, screen reader labels, touch target sizes (48x48dp minimum). Without explicit requirements, accessibility will be bolted on post-launch rather than built in. This is a reputational risk for a luxury brand.
Owner
Waruna + Sunthar to add minimum accessibility requirements to the PRD
G12
No Analytics/Event Tracking Spec
Medium PRD
Where
Only one event is mentioned in the entire PRD: insider_tip_expanded in Section 4.9. No other screen views, user actions, or conversion events are tracked.
Impact
No way to measure: feature adoption rates, decision/approval rates, time-to-approve, screen engagement duration, or drop-off points. Without analytics, the team cannot validate whether the Dynamic Trip Page is achieving its goals post-launch.
Owner
Sunthar to define an event tracking plan covering key user actions and screen views
G13
Image CDN Integration (V1.5)
Low PRD
Where
PRD Sections 7.4 and 7.6 reference image handling but note that CDN integration is not yet spec'd. This is acceptable for V1.
Impact
Low risk for April 15 ship. V1 uses direct image URLs from Notion. Image loading performance may be suboptimal on slower connections but is functional. CDN integration (responsive sizes, lazy loading, WebP conversion) is a V1.5 optimization.
Owner
Post-launch -- add to V1.5 backlog
G14
Date Parsing Fragility
Low PRD
Where
PRD Section 7.5 acknowledges that the date text field is "fragile". Ops enters dates as free text in Notion, meaning formats like "March 15", "15/03/2026", and "2026-03-15" could all appear.
Impact
V1 mitigation exists -- Kalpa's backend date parser handles common formats. V1.5 fix (proper Date-type fields in Notion) is planned. Risk is low for launch but increases as trip volume grows and ops enters more varied date formats.
Owner
Kalpa (V1 parser hardening) + Nirav (V1.5 Notion schema migration to Date fields)
